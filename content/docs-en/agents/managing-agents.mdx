# Managing Agents

## 1. Overview

The **Agents** page in the Web UI (`/agents`) displays all agents created in the tenant. Each agent is an independent AI entity with its own configuration: model, provider, context files, and behavior settings.

Two agent types:
- **predefined** — shared context for all users (SOUL.md, IDENTITY.md at agent level). Suitable for public bots, product assistants.
- **open** — each user has their own workspace and files. Suitable for personal assistants.

---

## 2. Creating a New Agent

Click **+ New Agent** to open the create dialog.

| Field | Description |
|-------|-------------|
| Display Name | Visible name (optional emoji) |
| Agent Key | Unique slug, auto-generated from name (e.g. `my-agent`) |
| Provider | Select a configured provider (dropdown) or type manually |
| Model | Select from the provider's model list or type manually |
| Agent Type | `predefined` (shared context) or `open` (per-user) |
| Description | Agent role description — used to auto-generate SOUL.md |
| Self Evolution | Allow agent to auto-update SOUL.md based on user feedback |

The **Check & Create** button verifies the model connection before creating. Once verified, the button changes to **Create**.

---

## 3. Agent Configuration

Click an agent in the list to open its detail view. The **Config** tab contains the main settings:

### Model and Provider

- **Provider** — registered provider name (e.g. `anthropic`, `openrouter`)
- **Model** — specific model name (e.g. `claude-sonnet-4-5-20250929`, `gpt-4o`)
- **Max Iterations** — maximum loop iterations per run (default: 20). Increase for agents with many complex tool calls.
- **History Limit** — number of user turns retained in history (`historyLimit`). Shorter history saves tokens; longer history helps the agent remember context.

---

## 4. Context Files

The **Files** tab in the agent detail view lets you manage files that define the agent's personality and knowledge.

### Standard Files

| File | Function |
|------|----------|
| `IDENTITY.md` | Agent name, role, background. Injected into system prompt at the "primacy zone". |
| `SOUL.md` | Main system prompt — communication style, values, processing principles. |
| `BOOTSTRAP.md` | If present, agent runs immediately on startup (mandatory notice). |
| `AGENTS.md` | Describes agents in the system so the main agent knows how to spawn sub-agents. |
| `TOOLS.md` | Documentation for available tools. |

### Custom Files

Any file can be added to the workspace. Files are injected into the system prompt under "Project Context" with a defensive preamble to protect the agent from being manipulated by external content.

---

## 5. Per-User Context Files

For **open agents**: each user has their own workspace directory (`base/{userID}/`). The following files are auto-created when a user chats for the first time:

- `USER.md` — personal information, preferences, history. The agent can update this file over time.

For **predefined agents**: the agent uses shared context (SOUL.md, IDENTITY.md) but still has a separate `USER.md` per user for storing personal information.

To view or edit a specific user's files, use the API or access the workspace directly.

---

## 6. Behavior Settings

In the **Config** tab, under Behavior:

| Setting | Description |
|---------|-------------|
| Debounce | Wait time (ms) before processing messages in group chat (prevents spam) |
| Streaming | Enable/disable streaming response by chunk. Disabling streaming helps with debugging. |
| Tool Status | Show tool call status in the UI (`tool.call` / `tool.result` events) |
| Input Guard | Enable prompt injection scanning (default: `warn` — logs but does not block) |

---

## 7. Sandbox Mode

Sandbox runs code inside Docker containers to isolate it from the main server.

| Field | Description |
|-------|-------------|
| Mode | `off` — no sandbox; `non-main` — sandbox sub-agents only; `all` — sandbox everything |
| Workspace Access | `none` full isolation; `ro` read-only mount; `rw` full read-write |
| Image | Docker image to use (e.g. `goclaw-sandbox:bookworm-slim`) |
| Scope | `session` — 1 container per session; `agent` — shared across sessions; `shared` — shared across all agents |
| Timeout | Maximum time (seconds) per command in the sandbox (default: 300) |
| Memory | Maximum RAM (MB) for the container (default: 512) |
| CPUs | Number of CPU cores (fractional allowed, e.g. `0.5`) |
| Network | Enable/disable network access from the container |

Sandbox requires Docker installed on the server. The image must be built in advance.

## 8. Rate Limits

The **Permissions** tab lets you set tool execution limits per agent:

- Limit the number of tool calls within a time window (per hour/day/week)
- Apply RBAC: `admin` / `operator` / `viewer`
- Deny specific tools for an agent via **Tool Policy**

---

## 9. Exporting and Importing Agents

Agent configuration is stored in PostgreSQL. To back up:

1. Use `GET /v1/agents/{id}` to retrieve the JSON configuration
2. Save all context files from the workspace (`SOUL.md`, `IDENTITY.md`, etc.)
3. To restore: `POST /v1/agents` with the same payload, then re-upload the files

---

## 10. Agent Sharing

Agents can be shared via a **pairing link** (external channel feature, e.g. Telegram):

- Each channel (Telegram, Zalo, Discord, etc.) has an `agent_key` linked to an agent
- Sharing links are generated from the Web UI or via WebSocket method `pairing.generate`
- Users who scan/click the link are connected to the corresponding agent

To restrict access: disable the channel or delete the agent.
